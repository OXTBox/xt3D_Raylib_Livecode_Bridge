# xt3d: notes for Claude Code

A bridge that lets LiveCode Script (LiveCode Community 9.6.3) drive raylib 6.2. Read `README.md` for the layout and conventions and `docs/STATUS.md` for what is proven and what is next. This file holds the things that are easy to get wrong.

## Who and where

- The owner wrote the original iGame3D (2007). He is fluent in LiveCode Script and rusty in C. Explain C and build steps plainly; he runs every Windows step by hand.
- This folder lives in WSL (`/home/igame3d/projects/xt3D_Raylib_Livecode_Bridge`). The build and LiveCode run on Windows. From WSL the Windows work folder is `/mnt/c/xt3d`; from Windows this folder is `\\wsl$\Ubuntu\home\igame3d\projects\xt3D_Raylib_Livecode_Bridge`.
- Nothing can be compiled for Windows or run in LiveCode from WSL. What can be checked here: `python3 gen_xt3d.py <raylib.h>` and `gcc -std=c99 -Wall -Wextra -fsyntax-only xt3d_shim.c` (needs `raylib.h` and `rlgl.h` beside it; copy them from `/mnt/c/xt3d/raylib-6.2_win64_msvc16/include/`). Say clearly which things were checked and which were not.

## Project intent

- A thin bridge, not an engine and not an editor. Do not rebuild iGame3D's mesh editor.
- Game logic stays in LiveCode Script. No Lua.
- The 3D view shares a window with LiveCode controls by rendering off-screen and copying each frame into a LiveCode image. Do not parent the raylib window into a LiveCode window unless the owner asks.
- Handler names follow raylib (`xt3d_DrawCube`) so agents can use raylib knowledge directly.
- Next major piece: an MCP link so Claude Desktop or a local model can call `xt3d_` handlers and see rendered frames (see `docs/STATUS.md`).

## Generated versus hand-written

- Generated by `gen_xt3d.py`: `xt3d_generated.inc`, `xt3d.lcb`, `xt3d_raylib_manifest.json`. Never edit these by hand; change the generator and re-run it.
- Hand-written: `xt3d_shim.c`. A new helper needs two edits: the C function in `xt3d_shim.c`, and an entry in the `EXTRA` list in `gen_xt3d.py` (name, return code, parameters, description) so it reaches the `.lcb` and the manifest.
- Type codes in the generator: `i` int, `u` unsigned, `f` float, `d` double, `b` bool, `l` long, `s` string, `p` pointer, `h` handle, `v` nothing.
- After any change to the shim or generator, all three of `xt3d_shim.c`, `xt3d_generated.inc`, `xt3d.lcb` must be rebuilt and reinstalled together with `build.bat`. A new `.lcb` with an old DLL fails with "Unable to bind foreign handler".

## Hard-won rules (each cost a crash or a failed build)

1. **Never return a C string to LiveCode Builder.** A foreign handler declared `returns ZStringNative` makes LCB free the returned pointer, which crashes on memory the DLL owns. Text results go through `xt_set()` in the shim, which fills a static buffer and returns the length; the `.lcb` reads bytes with `xt3d_ResultByte` and builds the string (`xtResult`). String parameters into C (`in ... as ZStringNative`) are fine.
2. **Every foreign call in LCB must be inside `unsafe ... end unsafe`.**
3. **Link with `/MD`.** The prebuilt raylib uses the DLL C runtime; without `/MD` the link fails with dozens of `__imp_` unresolved externals.
4. **No GPU call before a window exists.** `rl*` and most raylib functions dereference state created by `InitWindow`. New helpers that touch render state must start with `if (!IsWindowReady()) return;`.
5. **Do not init twice.** A second `InitWindow` orphans every GPU resource including the default font. `xt3d_InitWindow` and `xt3d_InitHidden` ignore the call if a window is ready.
6. **The Extension Builder must open `C:\xt3d\extension\xt3d.lcb`.** That folder has `code\x86_64-win32\xt3d.dll` beside it. Opening any other copy gives "unable to load foreign library".
7. **LiveCode must be closed while the DLL is copied**, or the copy silently leaves the old DLL in place.
8. **LCB library names:** namespace components must be lowercase letters (`org.xtalk.xtbridge`), or the compiler warns.
9. **Frame format.** LiveCode `imageData` is 4 bytes per pixel: one unused byte, red, green, blue, top row first. Render textures come back RGBA, bottom row first. `xt3d_RenderTextureToImageData` converts; drawing a render texture into another needs a negative source height to stay upright.
10. **Display scaling.** At 125% Windows scaling LiveCode stretches images by 1.25 and edges look rough. Set `the scaleFactor of stack` to `1 / the screenPixelScale` and render at real pixel size.
11. **raylib's MSAA flag does not apply to render textures.** Anti-aliasing in the image path is done by rendering at 2x and shrinking with bilinear filtering.

## Debugging on the owner's machine

A crash takes LiveCode straight to the desktop with no message. The method that works: a script that appends the name of each step to a log file before running it (`demos/xt3d_diagnostic.livecodescript.txt`), then read the last line after the crash. Ask for the log and for exact error text; LCB errors name the `.lcb` path and line, which also reveals which copy of the file was loaded.

Change one thing per round. Each round costs him a rebuild and often a LiveCode restart.

## Driving LiveCode from here (dev server)

When the owner has ticked "Dev server" in the test bench (`testbench/xt3d_testbench.livecodescript`, installed in `C:\xt3d\testbench\`), `tools/xt3d_dev.sh` talks to the running IDE: `ping`, `run '<statements>'` (inside the bench script), `eval`, `reload` (reopen the bench from its file after editing it), `snap` (PNG of the bench to `C:/xt3d/snap.png`, then Read it), `checks` (Run checks + results). It goes through Windows' `curl.exe`, because WSL2 cannot reach Windows' 127.0.0.1. No token file at `C:\xt3d\.xt3d_devtoken` means the server is not running: ask the owner to tick the box. Logs to read directly: `C:\xt3d\bench_checks.txt`, `C:\xt3d\raylib_log.txt`, and `C:\xt3d\livecode_errors.txt` (every LiveCode script error while the dev server runs, translated; `tools/xt3d_dev.sh errors`). The bench starts the server itself; opening `xt3d_devserver.livecodescript` directly also starts it.

Script-only stacks: if the owner saves one from the IDE, LiveCode writes its in-memory script over the file (and adds a UTF-8 BOM). That silently undid bench edits once. The owner should choose "Don't Save" when closing; if a file's first bytes are a BOM, check it against git before editing.

After editing a bench or server file, copy it to `C:\xt3d\testbench\` before `reload`. Building the DLL needs LiveCode closed (rule 7), which also stops the server.

## Old iGame3D formats (for importers)

- `.wtf` model: plain text. Line 1 `iGame3D Mdl`, then sections `#Bones:`, `#Vertices:` (count, then `x,y,z,boneIndex` per line), `#Paths:`, `#Groups:` (name, count, vertex indices), `#BoneOrientations:`, `#Edges:`, `#Materials:` (count; per material: name, a count of `key=value` lines, those lines, a triangle count, then `a,b,c,u1,v1,u2,v2,u3,v3` per triangle), `#Animations:`.
- `.emt` particle emitter: `key=value` lines (`texture`, `amount`, `emission rate`, `life`, `fade`, `size`, `speed`, `move`, `scale`, `num_textures`, `model`...). Some files have lost their line breaks.
- The original external API (176 `ig3d_` handlers with typed-suffix names) is in `reference/ig3d_2007_api_manifest.json`.
- Models exported by iGame3D use the opposite triangle winding to raylib.
